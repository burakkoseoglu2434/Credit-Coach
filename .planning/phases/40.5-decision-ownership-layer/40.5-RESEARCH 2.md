## Executive Summary

Phase 40.5 should be planned as a policy-owner phase, not as a calibration or funnel phase.

The safest shape is:

`Phase 40 summary normalization -> isolated decision helper -> raw roadmap summary write -> flat mirror -> business consumer alignment`

The code scan shows four important truths:

1. decision-critical fields already live closest to `run_recourse.py`
2. collection code still contains Phase 40 bridge logic that must stop evolving into a second policy owner
3. upstream `best.status` and `validate_plan(...)` remain useful ingredients, but they cannot stay the final business-visible decision source
4. messaging and live demo still have legacy `NEEDS_REVIEW` assumptions, so Phase 40.5 must finish with a clean three-state external contract

The clean split for this phase is therefore:

`decision helper contract -> deterministic gates and subtypes -> consumer and collection alignment`

## Concrete Repo Findings

### 1. Collection still carries bridge classification locally

`run_customer_artifact_collection.py` currently applies Phase 40 bridge logic like:

- zero-step -> `REJECTED`
- mismatch -> external `CONDITIONAL`, internal `NEEDS_REVIEW`
- else passthrough summary status

That was correct for Phase 40 trust repair, but it cannot grow into the final policy owner. Phase 40.5 must move the true ownership upstream and make collection a mirror only.

### 2. Raw summary is now strong enough to be the only policy input

`run_recourse.py` already exposes:

- decision bridge fields
- checkpoint status map
- raw contract health
- execution and realization probabilities

That is enough to support a single-source helper driven by `summary`.

### 3. Legacy `NEEDS_REVIEW` assumptions are still widespread

Search results show legacy `NEEDS_REVIEW` references in:

- `messaging.py`
- `test_messaging.py`
- `live-demo.ts`
- many batch and monitoring utilities

Phase 40.5 should only align the single-customer and collection-facing seams it owns. It should not redesign batch funnel semantics or portfolio calibration yet.

### 4. Existing tests already cover the right integration seams

- `test_recourse_redesign.py` already asserts normalized summary and raw roadmap behavior
- `test_customer_artifact_collection.py` already asserts flat mirroring and parity-safe collection outputs
- `test_messaging.py` already exercises narrative and decision-language behavior

Adding one dedicated decision-policy test module is likely the cleanest way to protect:

- gate ordering
- internal vs external mapping
- subtype priority
- payload completeness

## What Phase 40.5 Must Deliver

### 1. One canonical decision payload

The helper must always return a full payload with:

- external status
- internal status
- confidence
- readiness
- one-line reason
- primary reason code
- numeric drivers
- subtype fields
- upgrade condition
- realization anchor
- strong execution flag
- offer maturity
- policy version
- gate trace

This payload must be the only source used by raw artifact write and flat mirror write.

### 2. Internal-first ordered decision evaluation

The context already locked the order:

`REJECTED -> APPROVED -> CONDITIONAL -> NEEDS_REVIEW`

Research confirms the safest implementation is one isolated helper that computes internal policy first and only then maps to the business-visible three-state contract.

### 3. Explanation contract is part of ownership, not a later accessory

`DEC-02` requires every non-rejected customer to carry:

- one-line business explanation
- structured numeric drivers
- confidence
- expected readiness
- upgrade condition

This belongs in the same helper contract because explanation quality depends on the same gates and subtypes.

### 4. Offer maturity must be translated into decision ownership

`DEC-03` is not an offer-optimization problem anymore. It is a decision ownership truth:

- `inactive` or `provisional` offer cannot become externally `APPROVED`
- `active_rankable` offer can support approval if other gates pass
- no offer branch must force `offer_maturity = none`

### 5. Business consumers should consume, not infer

Phase 40.5 should end with:

- collection code mirroring decision payload only
- messaging speaking only in `APPROVED | CONDITIONAL | REJECTED`
- live demo not needing legacy fallback to explain business-visible decision state

## Main Risks

### Risk 1: Collection becomes a second decision engine

If collection keeps recomputing or repairing policy outcomes locally, parity will regress.

Mitigation:

- helper runs only in producer seam
- collection only mirrors payload and validates parity

### Risk 2: Internal exception state leaks into business surfaces

The repo still has many legacy `NEEDS_REVIEW` branches.

Mitigation:

- external mapping happens last
- explicit leak-guard tests
- consumer alignment limited to single-customer and collection-facing surfaces

### Risk 3: Explanation fields drift from actual gates

If reason summary, subtype, and upgrade condition are assembled outside the policy helper, the system will look deterministic while actually carrying split logic.

Mitigation:

- explanation and subtype contract come from the same helper output

### Risk 4: Phase 40.5 accidentally expands into calibration

Threshold tuning, policy comparison, and approve-rate optimization belong to Phase 41.

Mitigation:

- keep fixed thresholds in this phase
- no cohort-level tuning loop
- no funnel target optimization inside execution scope

## Recommendation

Proceed with planning immediately.

The phase is now sufficiently bounded:

- Phase 40 already repaired contract integrity
- Phase 40.5 can now own deterministic customer decisions
- Phase 41 can later evaluate whether those fixed thresholds hit the milestone North Star

The implementation should prefer one new helper module plus narrow wiring changes over spreading decision rules across multiple existing files.
