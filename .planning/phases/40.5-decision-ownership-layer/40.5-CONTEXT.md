# Phase 40.5: Decision Ownership Layer - Context

**Gathered:** 2026-03-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Turn the repaired Phase 40 contract surface into a deterministic decision layer with explicit external and internal decision ownership.

Phase 40.5 owns:
- final customer-level decision semantics
- deterministic decision ordering
- decision thresholds and bridge rules
- internal vs external decision mapping
- decision explanation contract
- decision ownership fields in raw and flat artifacts

Phase 40.5 does **not** own:
- cohort calibration or threshold tuning loops
- portfolio funnel rollups
- operator packet presentation
- planner source-mix recovery
- pilot refresh workflow or institution docs

Those remain in later phases:
- Phase 41 for cohort and calibration
- Phase 43 for operator packs
- Phase 42 for planner quality
- Phase 44 for production pilot baseline

</domain>

<decisions>
## Implementation Decisions

### 1. Exact Scope Of Phase 40.5
- Phase 40.5 adds one deterministic **customer-level decision policy layer** on top of the repaired Phase 40 artifact contract.
- The policy owner should sit **after** Phase 40 normalization and **before** raw and flat artifact write.
- `best_status` and plan-level `PlanRecord.status` remain legacy upstream ingredients, not the final customer-facing owner.
- Phase 40.5 may add a dedicated decision helper module or a clearly isolated policy seam, but it must not push new decision logic into:
  - website consumers
  - collection summary formatting
  - portfolio calibration logic
- The deliverable is not just a field rename. It must produce:
  - business-visible decision ownership
  - internal decision ownership
  - deterministic reasons
  - deterministic subtypes
  - deterministic bridge behavior for exceptions

### 2. Final Decision Field Set
- Raw `customer_roadmap.json` canonical home remains `summary`.
- Flat `customer_metrics.csv` mirrors the same fields.
- Required Phase 40.5 decision fields:
  - `decision_status`
    - external/business-visible
    - allowed values: `APPROVED | CONDITIONAL | REJECTED`
  - `decision_status_internal`
    - internal-only
    - allowed values: `APPROVED | CONDITIONAL | REJECTED | NEEDS_REVIEW`
  - `decision_policy_version`
    - deterministic policy identifier
    - initial value: `v2.1_phase_40_5`
  - `decision_confidence`
    - `[0.0, 1.0]`
    - deterministic composite confidence
  - `expected_readiness`
    - canonical values:
      - `now`
      - `week_4`
      - `week_12`
      - `week_24`
      - `not_ready`
      - `unknown_review`
  - `decision_reason_summary`
    - one-line business-safe explanation
  - `decision_reason_primary`
    - short primary reason code
  - `decision_reason_drivers`
    - max `3` structured drivers
    - raw JSON list in roadmap summary
    - `decision_reason_drivers_json` mirror in flat outputs
  - `rejection_type`
    - allowed values:
      - `NO_PATH`
      - `LOW_IMPACT`
      - `LOW_EXECUTION`
    - null for non-rejected decisions
  - `conditional_type`
    - allowed values:
      - `EXECUTION_GATED`
      - `TIME_GATED`
      - `OFFER_GATED`
      - `DATA_ISSUE`
    - null for non-conditional decisions
  - `upgrade_condition`
    - null for `APPROVED`
    - required for `CONDITIONAL`
    - optional but recommended for `REJECTED`
  - `realization_anchor`
    - deterministic policy anchor used in thresholds
  - `strong_execution_flag`
    - `1` if strong execution threshold passes
  - `offer_maturity`
    - allowed values:
      - `none`
      - `inactive`
      - `provisional`
      - `active_rankable`
  - `decision_gate_trace`
    - internal JSON payload for debugging and validation
    - not required on business-facing surfaces

- Structured driver shape is fixed:
  - `driver_key`
  - `current_value`
  - `target_value`
  - `unit`
  - `source_field`
  - `comparison`
- Drivers should be numeric whenever possible.
- Example:
  - `utilization_pct: 82 -> 50`
  - not `high utilization`

### 3. Deterministic Decision Ordering
- Decision ordering is fixed and must be enforced exactly:
  1. `REJECTED`
  2. `APPROVED`
  3. `CONDITIONAL`
  4. `NEEDS_REVIEW`
- Exception logic may **never** override a valid earlier class.
- Ordering applies to **internal** decision evaluation first.
- Business-visible decision is then derived from the internal decision through fixed mapping rules.

### 4. Deterministic Decision Inputs And Anchors
- Phase 40.5 should compute policy from normalized Phase 40 fields plus best-plan truth.
- Canonical inputs:
  - `best_action_count`
  - `zero_step_flag`
  - `raw_contract_pass`
  - `parity_pass`
  - `data_issue_flag`
  - `credit_readiness_stage`
  - `approval_ready_4w`
  - `approval_ready_12w`
  - `approval_ready_24w`
  - `plan_execution_probability`
  - `approval_dependent_plan_probability`
  - `offer_acceptance_probability`
  - `combined_plan_realization_probability`
  - `expected_pd_improvement`
  - `nominal_pd_improvement`
  - `local_explainability_confidence`
  - `best_constraint_status`
  - `approval_pending_action_count`
  - `rankable_offer_count`
  - `offer_plan`
- Canonical bridge inputs added in this phase:
  - `expected_pd_improvement`
  - `nominal_pd_improvement`
  - `offer_maturity`

- `realization_anchor` rule:
  - if `combined_plan_realization_probability > 0`, use it
  - else use `plan_execution_probability`
- `strong_execution_flag` rule:
  - `1` when `plan_execution_probability >= 0.50`
  - else `0`
- `expected_readiness` rule:
  - use normalized `credit_readiness_stage` if valid
  - map:
    - `not_ready_yet -> not_ready`
    - invalid or conflicting readiness -> `unknown_review`
- `offer_maturity` rule:
  - `none`
    - no offer-bearing branch
  - `inactive`
    - offer exists but terms are incomplete, placeholder-like, or not executable
  - `provisional`
    - approval pending / dependency gated / institution-side branch not fully executable
  - `active_rankable`
    - rankable offer branch, complete terms, approval not pending

### 5. Decision Confidence Rule
- `decision_confidence` is required in Phase 40.5.
- It must be deterministic and computed from already available ingredients.
- Canonical formula:
  - `execution_component = realization_anchor`
  - `readiness_component =`
    - `1.00` for `now` or `week_4`
    - `0.65` for `week_12`
    - `0.45` for `week_24`
    - `0.20` for `not_ready`
    - `0.10` for `unknown_review`
  - `impact_component = min(1.0, expected_pd_improvement / 0.05)`
  - `explainability_component = local_explainability_confidence if present else 0.50`
  - `contract_component =`
    - `1.00` if `raw_contract_pass == 1` and `parity_pass == 1` and `data_issue_flag == 0`
    - else `0.35`
- Final score:
  - `decision_confidence = round(0.35*execution_component + 0.25*readiness_component + 0.20*impact_component + 0.10*explainability_component + 0.10*contract_component, 4)`
- Confidence is used as a real gate, not only as a reporting field.

### 6. Decision Rules For REJECTED
- `REJECTED` wins first.
- Reject if any of the following hold:
  - `best_action_count == 0`
  - `zero_step_flag == 1`
  - no viable best path
  - invalid best path
  - `best_constraint_status == invalid`
  - `expected_pd_improvement < 0.01`
  - `realization_anchor < 0.10`
- Rejection subtype assignment:
  - `NO_PATH`
    - zero-step
    - invalid best path
    - no viable plan
  - `LOW_IMPACT`
    - `expected_pd_improvement < 0.01`
    - and path is otherwise executable
  - `LOW_EXECUTION`
    - `realization_anchor < 0.10`
    - and there is a nonzero path but it is not realistically realizable
- Rejected outputs:
  - internal `REJECTED`
  - external `REJECTED`
  - `conditional_type = null`
  - `upgrade_condition` optional

### 7. Decision Rules For APPROVED
- `APPROVED` is evaluated only if not rejected.
- All of the following must hold:
  - `best_action_count > 0`
  - `raw_contract_pass == 1`
  - `parity_pass == 1`
  - `data_issue_flag == 0`
  - `decision_confidence >= 0.60`
  - `realization_anchor >= 0.50`
  - `expected_pd_improvement >= 0.02`
  - `expected_readiness in {now, week_4}`
  - `approval_ready_4w == 1` **or** `strong_execution_flag == 1`
  - `offer_maturity not in {inactive, provisional}`
- `APPROVED` may occur with:
  - no offer branch
  - active rankable offer branch
- `APPROVED` can never occur when:
  - `expected_readiness in {week_12, week_24, not_ready, unknown_review}`
  - internal exception bucket is active
  - offer branch is inactive or provisional

### 8. Decision Rules For CONDITIONAL
- `CONDITIONAL` is evaluated only if not rejected and not approved.
- Policy-conditional branch requires:
  - `best_action_count > 0`
  - `realization_anchor >= 0.20`
  - `expected_pd_improvement >= 0.01`
  - `decision_confidence >= 0.40`
- Canonical subtype priority:
  1. `DATA_ISSUE`
  2. `OFFER_GATED`
  3. `TIME_GATED`
  4. `EXECUTION_GATED`
- Subtype rules:
  - `OFFER_GATED`
    - `offer_maturity in {inactive, provisional}`
  - `TIME_GATED`
    - `expected_readiness in {week_12, week_24}`
    - or viable path exists but 4-week readiness is not there yet
  - `EXECUTION_GATED`
    - `realization_anchor in [0.20, 0.50)`
    - or strong path exists but execution is not strong enough for approval
  - `DATA_ISSUE`
    - only through bridge mapping from internal exception state
- `upgrade_condition` is mandatory for every conditional record.
- `upgrade_condition` must be numeric and driver-aligned.
- Bad example:
  - `financial situation improves`
- Good example:
  - `Utilization 82% -> below 50% and 4-week gate passes`

### 9. Decision Rules For NEEDS_REVIEW (Internal Only)
- `NEEDS_REVIEW` is internal-only and exception-only.
- It is evaluated last.
- It may occur only when the customer is not already rejected, approved, or policy-conditional.
- Internal `NEEDS_REVIEW` triggers:
  - `raw_contract_pass == 0`
  - `parity_pass == 0`
  - `data_issue_flag == 1`
  - `decision_confidence < 0.40`
  - missing decision ingredient after Phase 40 normalization
  - impossible combination of readiness, probabilities, or offer maturity
- Additional confidence rule:
  - `decision_confidence < 0.40` -> internal `NEEDS_REVIEW`
  - `decision_confidence >= 0.30` is still the lower bridge floor for safe external `CONDITIONAL`
- If `decision_confidence < 0.30` and reject rules do not fire:
  - internal remains `NEEDS_REVIEW`
  - external still maps to safe `CONDITIONAL`
  - subtype defaults to `DATA_ISSUE` unless a stronger outward-safe subtype already exists

### 10. Mapping Rules Between Internal And External Decisions
- External business-visible mapping is fixed:
  - internal `APPROVED` -> external `APPROVED`
  - internal `CONDITIONAL` -> external `CONDITIONAL`
  - internal `REJECTED` -> external `REJECTED`
  - internal `NEEDS_REVIEW` -> external `CONDITIONAL`
- `NEEDS_REVIEW` must never leak into:
  - `customer_roadmap.json` business-visible surfaces
  - `customer_metrics.csv` business-visible consumers
  - website/business-facing outputs
- Internal review mapping detail:
  - data issue or parity mismatch -> external `CONDITIONAL` with `conditional_type = DATA_ISSUE`
  - low-confidence non-rejected case -> external `CONDITIONAL` with dominant outward-safe subtype if available, else `DATA_ISSUE`
- External inconsistency or data issues must not become default customer rejection.

### 11. Threshold Rules And Bridge Rules
- Fixed thresholds for Phase 40.5:
  - `APPROVED`
    - `realization_anchor >= 0.50`
    - `expected_pd_improvement >= 0.02`
    - `decision_confidence >= 0.60`
  - `CONDITIONAL`
    - `realization_anchor >= 0.20`
    - `expected_pd_improvement >= 0.01`
    - policy-conditional confidence `>= 0.40`
  - internal review confidence threshold:
    - `< 0.40`
  - bridge confidence floor:
    - `< 0.30` stays internal review, external safe conditional
- Approved-threshold widening already accepted for this phase:
  - `4w gate` **or** `strong_execution_flag`
  - not `4w gate` only
- Offer bridge rules:
  - `inactive` offer -> `CONDITIONAL / OFFER_GATED`
  - `provisional` offer -> `CONDITIONAL / OFFER_GATED`
  - `active_rankable` offer -> approval may still be possible if all other gates pass

### 12. Edge-Case Handling
- `best_action_count == 0`
  - always `REJECTED`
  - always `rejection_type = NO_PATH`
- Raw or flat mismatch
  - internal `NEEDS_REVIEW`
  - external `CONDITIONAL`
  - `conditional_type = DATA_ISSUE`
- Missing required decision ingredient after Phase 40 normalization
  - internal `NEEDS_REVIEW`
  - external `CONDITIONAL`
- `expected_readiness in {week_12, week_24}`
  - can never be externally `APPROVED`
- `expected_readiness == unknown_review`
  - internal `NEEDS_REVIEW`
  - external `CONDITIONAL`
- Offer branch inconsistency
  - if `offer_plan == 1` but offer maturity cannot be classified safely
  - internal `NEEDS_REVIEW`
  - external `CONDITIONAL`
- Legacy `best_status` disagreement with final decision
  - final decision fields win
  - `best_status` is retained only as compatibility history

### 13. Acceptance Criteria
- Every raw single-customer artifact has:
  - `decision_status`
  - `decision_status_internal`
  - `decision_policy_version`
  - `decision_confidence`
  - `expected_readiness`
  - `decision_reason_summary`
  - subtype fields
- Every flat customer-level collection row mirrors the same final decision truth.
- Business-visible states are only:
  - `APPROVED`
  - `CONDITIONAL`
  - `REJECTED`
- Internal `NEEDS_REVIEW` appears only in exception cases and never leaks externally.
- `step_count == 0` always yields:
  - external `REJECTED`
  - internal `REJECTED`
  - `rejection_type = NO_PATH`
- `expected_readiness in {week_12, week_24}` never yields external `APPROVED`.
- `offer_maturity in {inactive, provisional}` never yields external `APPROVED`.
- Every `CONDITIONAL` record has:
  - `conditional_type`
  - `upgrade_condition`
- Every non-approved record has:
  - `decision_reason_summary`
  - structured numeric drivers
- Decision ownership is deterministic and versioned.

### 14. Outputs And Artifacts
- Updated raw artifacts:
  - `customer_roadmap.json`
  - `metrics.json`
  - `decision_log_record.json`
- Updated flat artifacts:
  - `customer_metrics.csv`
  - `customer_selection.csv` if needed for policy-version visibility
- Updated business-safe consumer outputs:
  - website/live demo uses only external decision fields
  - narrative decision cards move from legacy `NEEDS_REVIEW` logic to `CONDITIONAL`
- Updated tests:
  - single-customer decision policy tests
  - collection-level mirror tests
  - internal/external mapping tests
  - threshold edge-case tests

### 15. Recommended Implementation Order
- First, add final decision vocabulary and field set to schema-safe artifact contracts.
- Second, surface all required decision inputs into normalized raw summary and flat metrics:
  - especially `expected_pd_improvement`
  - `nominal_pd_improvement`
  - offer maturity ingredients
- Third, implement one isolated decision ownership helper:
  - input: repaired summary + best-plan ingredients + metrics ingredients
  - output: final decision payload
- Fourth, wire the helper into raw roadmap and metrics generation in `run_recourse.py`.
- Fifth, mirror the final decision payload into collection outputs without recomputation.
- Sixth, align business-facing consumers and messaging to the new three-state external decision contract.
- Seventh, add regression coverage for all ordered rules and bridge mappings.

### Claude's Discretion
- Exact helper/module name for the decision owner
- Whether `decision_reason_drivers` lives as nested JSON only or also as flattened columns
- Exact `decision_gate_trace` payload shape, as long as the ordered gates remain testable
- Whether `expected_readiness` is computed in the decision helper or fed from a precomputed normalization helper

<specifics>
## Specific Ideas

- The user explicitly wants this phase to be the moment where the system becomes **decision-owning**, not only artifact-clean.
- The most important business truth:
  - external surfaces must say one of `APPROVED | CONDITIONAL | REJECTED`
  - internal `NEEDS_REVIEW` may exist but only as an exception/debugging bucket
- The most important safety truth:
  - inconsistency or data issues are system issues, not automatic customer rejection
  - therefore inconsistency maps externally to `CONDITIONAL`, not `REJECTED`
- The biggest legacy seam today:
  - `safety.validator.validate_plan(...)` still emits legacy plan status
  - that status is useful as an input, but must stop being the final customer-facing decision owner

</specifics>
